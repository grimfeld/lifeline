# The Private folder is a gate at Core's read layer, not encryption

Some notes should not be on screen when someone else is at the user's unlocked laptop or picks up the phone: a reserved `Private` folder, behind a password. The threat is eyes at the device, not the server, the backups or a stolen disk — one user, self-hosted (ADR 0002), already owns the account and the Fly volume. So the decision is a **gate, not a safe**: the Documents in `Private` (and below it) are stored, synced and indexed exactly like any other Document, in plaintext, and Core's one document store filters them out of every read while the folder is **locked**. Locked is the default on every device — after a reload, after ten idle minutes, after the app goes to the background, and on a device that has not yet pulled the settings while a `Private` folder has notes — and unlocking lives in memory only. Absent means absent from everything at once: the Vault tree (the folder node itself stays, closed), full-text search, links, backlinks and unlinked mentions, the Graph, Bases, Cards, `[[` autocomplete and the tag vocabulary; a link into the folder shows a lock and asks for the password rather than pretending the target does not exist, since an "unresolved" link would offer to create a duplicate. The password is the user's own — not the account's — and only its salted PBKDF2 hash is stored, in a synced settings Document, so every device shares one password and unlocks offline; resetting it needs the account password, online, and loses nothing because nothing is encrypted. Only body-first types (Note, Clipping, Writing) may be created in or moved into `Private`: a hidden Task is lost work, not privacy. Anything that must see every body — Attachment clean-up (ADR 0037) — refuses to run while locked rather than reading around the filter; the filter has no bypass, on purpose.

## Considered options

- **Client-side encryption (password-derived key, ciphertext at rest and in PocketBase)** — rejected for now: the derived index (ADR 0009) goes blind to whatever is encrypted — no links, backlinks, search or tags for those notes — and a forgotten password is data gone for good. Real secrecy against the server is not the threat, and the gate can be upgraded later: `Private` would simply become the set of Documents whose body is encrypted.
- **A lock only in the Vault tree** — rejected: search, backlinks, the Graph and any Base list the same Documents; a tree-only lock leaks in one keystroke. One filter in the store, zero surface patches.
- **Any folder markable private (a synced list of paths)** — rejected: folders are not records (ADR 0013), so marks need their own store and every folder rename and move has to rewrite them; one reserved name costs nothing and is that list with one entry.
- **Reusing the PocketBase account password on unlock** — rejected: unlocking would need the network in an offline-first app.
- **A per-device local PIN** — rejected: a fresh device would show everything until its PIN was set, and the user would have to remember which device had which PIN.
- **Letting Attachment clean-up read the raw store while locked** — rejected: a second read path around the filter that every future "scan all bodies" feature would have to remember to copy.

## Consequences

- `Private` joins `Templates` and `Journal` as a reserved folder name; a plain folder already called `Private` is adopted when the user sets the password.
- The gate is a runtime signal (locked / unlocked) that Core's document reads consult; Apps and surfaces never check it themselves, and nothing outside Core reads the `documents` table directly for body-first types.
- Locked Documents still sync, still take part in the derived index, and still count in Dexie; only reads through Core drop them. A locked device can therefore never write to a private Document either — the editor never sees one.
- The Tasks App's own occurrence lookups bypass the store by design (composite indexes on internal types) and are unaffected: nothing Schedulable can live in `Private`.
- The lock state is per device and per tab; a manual "Lock private notes" Command exists beside the timeout.
