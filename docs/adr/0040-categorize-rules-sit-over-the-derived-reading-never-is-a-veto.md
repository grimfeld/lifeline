# Categorize rules sit over the derived reading, and never is a veto

Auto-categorization has been a *reading* since ADR 0033: the category you last gave a payee is what the next import gets suggested, derived on the spot, nothing stored, nothing to maintain. It is right most of the time and self-correcting — recategorize once and every later import follows. But it is a reading, and two things a reading cannot know have no home: "this payee always means that Category, whatever I did last time", and "never guess for this payee at all". The second is the sharper one. Amazon is one payee for books, cables, nappies and a birthday present; the last-used category is not a signal there, it is a coin toss that arrives pre-ticked in the import preview and quietly lands wrong. So a **Categorize rule** is added: the user's own word about a payee, stored, laid over the derived reading — either a Category it always hands out, or **never**, a veto that keeps the payee out of auto-categorization entirely so its rows land in the uncategorized inbox where a human picks. A rule reads its text against the normalized payee (the bank's casing, digits and punctuation collapse, as everywhere else in the Ledger), *contains* by default and *exact* when the whole payee is meant. Precedence is fixed and small: a never rule beats a category rule, an exact rule beats a contains rule, the longest match beats a shorter one, and any rule beats history. A rule's kind is never typed in — a category rule speaks for its Category's own kind, a never rule for both. Rules change nothing but what is *suggested*: the import preview and the Auto-categorize sweep are still where a human sees it, and nothing is ever written into the ledger unwitnessed.

The rules also get the one place they were missing: a **Rules** tab in the Register showing every auto-categorization the ledger would make — the hand-made rules on top, and under them the derived reading itself, payee by payee, which is where most of the work happens and which was invisible before. A derived line can be pinned into a rule (it then stops moving with the ledger) or vetoed with never, in one tap.

## Considered options

- **Leave it derived and fix mistakes afterwards** — rejected: it is what happens today, and for Amazon the fix never converges. Recategorizing the last Amazon row does not teach the ledger anything true; it just changes which wrong category the next import pre-ticks. The user has a fact the ledger cannot derive ("this payee carries no category"), and there is nowhere to put it.
- **A blacklist of payee strings, separate from rules** — rejected: two stores, two editors and two places to look for "why was this categorized?". A never rule *is* a rule with no Category, and the veto is exactly the precedence question a single ordered list already answers.
- **Rules replace the history-derived reading entirely** — rejected: the reading is the feature. Hundreds of payees categorize themselves with nothing typed in; making the user write a rule per merchant is the maintenance ADR 0033 refused. Rules are the exception layer and stay small on purpose.
- **Rules with an explicit priority number, dragged into order** — rejected: a hand-kept ordering is a second thing to maintain and to get wrong. Veto > exact > longest match is derived from the rules themselves, explains itself in one line, and is stable when rules are added.
- **A rule kind ("applies to expenses / income / both") on the form** — rejected as an input: a category rule's Category already knows its kind, so asking again invites the two to disagree. The field is stored (the matcher reads it) but stamped by the write path and guarded, never typed.
- **Symmetric contains, as the history matcher uses** — rejected for rules: history compares two payees, where either may be the noisier spelling, so symmetry is right there. A rule is a fragment the user wrote; letting a shorter payee match a longer rule would make rules quietly wider than they read.
- **Rules that also rewrite payees, set tags, or split amounts** — rejected: that is an import scripting language, and every one of those is a different feature with its own witness problem. A rule answers one question — which Category, or none.
- **Applying rules retroactively over the whole ledger on save** — rejected (superseded in part by ADR 0107: a rule may recategorize history, but only through a preview the user confirms; never silently on save): a rule is about what gets *suggested*, not a bulk edit that silently rewrites facts. The Auto-categorize sweep already exists for the inbox, obeys rules, and shows what it did; recategorizing history is the Base's job, in front of the user.

## Consequences

- A new internal `ledger_rule` type: `match`, `mode` (contains / exact), `kind` (stamped from the Category, "both" for a never rule, guarded), `categoryId`, `never`. Internal, so it stays out of the Vault tree and link completion, and still gets a Base like everything else.
- `suggestCategory` takes the rules as a fourth argument and answers `confidence: "rule"` when one speaks; a never rule makes it answer nothing at all. Its callers — the import preview and the sweep — pass them; existing calls without rules behave exactly as before.
- The import preview marks rows `rule` and `never` beside the old `auto`, so it is legible why a row is pre-ticked or deliberately blank. The sweep reports how many rows a never rule left alone rather than counting them as failures.
- Two rules with the same text, mode and reach are refused at the write path — the first is there to edit. Precedence handles overlap; duplicates only produce arguments.
- The Rules panel shows each rule's coverage — how many payees in the ledger it actually decides, precedence applied — so a rule shadowed by a broader never rule reads as the 0 it is, and a typo'd rule reads as 0 too.
- Nothing migrates: with no rules, auto-categorization is exactly ADR 0033's reading. Deleting a rule falls back to that reading rather than to nothing.
